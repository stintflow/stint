## 1. Análise (HEAD `b1f4579`)

### 1.1 Como o Stint carrega as funções do jq
- `JqExpressionEvaluator` (`stint-core`, construtor) chama `BuiltinFunctionLoader.getInstance().loadFunctions(classLoader, JQ_1_6, rootScope)` do jackson-jq 1.6.0.
- O loader tem duas fontes:
	- **funções Java** (`type`, `length`, `keys`, `tostring`, ... — 81 classes), achadas por `ServiceLoader` no `META-INF/services/net.thisptr.jackson.jq.Function` do jar;
	- **funções definidas em jq** (`map`, `select`, `to_entries`, ...), lidas do recurso `net/thisptr/jackson/jq/jq.json`, que muitas delas usam por baixo das funções Java.
- O jar do jackson-jq traz metadados nativos próprios (`META-INF/native-image/…`): o recurso `jq.json` e a reflexão do `JqJson`. **Nada sobre os provedores de `ServiceLoader`**: ele conta com o `ServiceLoaderFeature` do GraalVM, ligado por padrão.

### 1.2 Por que quebra no Quarkus nativo
- O Quarkus passa `-H:-UseServiceLoaderFeature` ao `native-image` (visto no comando do build do sandbox, Quarkus 3.33.2) e registra só os serviços que alguma extensão declara (`ServiceProviderBuildItem`). Nenhuma extensão declara os do jackson-jq.
- No binário, `ServiceLoader.load(Function.class)` não acha nenhum provedor. O `JqExpressionEvaluator` sobe sem erro, mas qualquer expressão que chame uma função Java falha na avaliação (`Failed to evaluate jq expression: …`).
- **Reproduzido no sandbox** (S.4, 8i): o `place-order` valida a entrada com `(.orderId | type) != "string" or …` e falha na 1ª ativação. Com `-Dquarkus.native.auto-service-loader-registration=true` (o Quarkus registra todo `META-INF/services` do classpath), o caminho feliz passa.

### 1.3 Por que os testes do Stint não pegaram
- O único teste nativo é o `stint-example-aws-smoke` (2.7, `native.yml`). O `aws-smoke.yaml` só usa caminhos: `${ .name }`, `${ . }`, `${ $context }`. Nenhuma função.
- O `docs/connectors.md` diz "Native: proven by `stint-example-aws-smoke`", o que é verdade só para expressões sem função.

### 1.4 Onde a correção pode morar
- O Stint **não tem extensão Quarkus própria**: os bundles (`stint-bundle-aws`, `stint-bundle-local`) são jars comuns. Não há `@BuildStep` onde declarar um `ServiceProviderBuildItem`.
- O que funciona com qualquer build nativo (Quarkus ou `native-image` puro) são os **metadados de alcance no próprio jar**: `META-INF/native-image/<groupId>/<artifactId>/{reflect,resource}-config.json`, que o `native-image` lê de todo jar do classpath. Com o arquivo de serviço incluído como recurso e as classes dos provedores registradas para reflexão (construtor sem argumentos), o `ServiceLoader` acha e instancia os provedores mesmo com o feature desligado. É o mesmo par de registros que o `ServiceProviderBuildItem` do Quarkus produz.

## 2. Problema e objetivo
**Problema.** Numa imagem nativa feita pelo Quarkus, toda expressão jq com função Java falha. O 2.7 promete imagem nativa e o consumidor só descobre em produção.

**Objetivo.** O jar do `stint-core` levar o que a imagem nativa precisa para carregar as funções do jq, sem nenhuma configuração do consumidor, e o smoke nativo provar isso.

## 3. Requisitos
- **RF1** — `stint-core` declara, em `META-INF/native-image/io.stintflow/stint-core/`, o recurso `META-INF/services/net.thisptr.jackson.jq.Function` e a reflexão (construtor sem argumentos) de cada provedor listado nele, para a versão do jackson-jq do BOM do Stint.
- **RF2** — Um teste unitário falha se a lista do RF1 e o arquivo de serviço do jackson-jq do classpath divergirem (atualização do jackson-jq não pode deixar o nativo quebrado em silêncio).
- **RF3** — O smoke AWS passa a avaliar uma função builtin num caminho que o `AwsSmokeIT` verifica, para o `native.yml` cobrir isso.
- **RF4** — Docs: `docs/connectors.md` (Native) e o README dizem que as funções do jq estão cobertas no nativo e por qual mecanismo.

## 4. Especificação
- `stint-core/src/main/resources/META-INF/native-image/io.stintflow/stint-core/resource-config.json`:
	```json
	{ "resources": { "includes": [ { "pattern": "\\QMETA-INF/services/net.thisptr.jackson.jq.Function\\E" } ] } }
	```
- `…/reflect-config.json`: um item por provedor, `{"name": "<classe>", "methods": [{"name": "<init>", "parameterTypes": []}]}`, na ordem do arquivo de serviço.
- `JqNativeMetadataTest` (`stint-core`, unitário): lê o arquivo de serviço do jackson-jq pelo classloader e o `reflect-config.json` do `stint-core`, e exige o mesmo conjunto de classes; e exige que o `resource-config.json` inclua o arquivo de serviço.
- `aws-smoke.yaml`: a entrada da task ganha `nameLength: ${ .name | length }`, o worker de eco a devolve, e o `AwsSmokeIT` verifica `nameLength == 5` (para `"smoke"`) no contexto e no evento emitido. O mesmo IT roda no JVM (`it.yml`) e no nativo (`native.yml`).
- Nenhuma mudança de API, SPI ou comportamento no JVM.

## 5. Fora de escopo
- Uma extensão Quarkus do Stint (seria o lugar natural para `ServiceProviderBuildItem`, mas é bem maior que esta correção).
- Trocar o jackson-jq ou carregar as funções sem `ServiceLoader`.
- Mudar como uma instância `FAILED` loga a causa (observação 5.5 do gate: hoje o engine registra só a mensagem). Fica como observação para o plano.

## 8. Questões em aberto: propostas para aprovação

### 8a. Como provar o smoke nativo localmente (CA3)
- O `AwsSmokeIT` nativo (`@QuarkusIntegrationTest`) roda o binário como processo do host. No Windows, um binário Linux do build em container não roda, e por isso o CA2 do 2.7 ficou para o `native.yml` no GitHub Actions.
- **Proposta:** construir com `-Dquarkus.native.remote-container-build=true` (o Docker Desktop no Hyper-V não monta `C:`, S.4 8f do sandbox), rodar o binário num container `ubi9-quarkus-micro-image:2.0` na rede do compose do sandbox (floci) e fazer o mesmo `POST` e as mesmas verificações do `AwsSmokeIT` por `curl` e `aws`, registrados em `2.10-CA3.txt`.
- O `native.yml` continua sendo a prova oficial; disparar o workflow é do Kayan (ele roda por `workflow_dispatch`).

### 8b. O contorno do sandbox
- Depois do CA4, o `quarkus.native.auto-service-loader-registration=true` do sandbox pode sair. **Proposta:** sai num commit `sdd-s4:` do sandbox, com a seção 8i do S.4 marcada "resolvido no 2.10", e o README do sandbox atualizado.
