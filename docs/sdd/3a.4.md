### 1.2 O que mudou desde o rascunho e entra aqui
- **3a.1:** `call: decision` compila para `call: remote` + `switch <tarefa>/route`; `onUncertain` aponta para uma tarefa, e **não há caminho para voltar ao ramo da opção** que o humano escolher. O registro de decisão fica em `InstanceSnapshot.decisions`, por ponteiro (5.4).
- **3a.2 / 3a.2b:** `ConfidenceCalibration` por adapter, com `stint.decision.adapters.<id>.calibration.temperature`. No CA6 do 3a.2b, o LitJev com Qwen3.5-2B ficou muito confiante nos erros: correções humanas são o único sinal para calibrar.
- **3a.5:** nível por instância; conteúdo restrito só em blobs criptografados (E1); fato restrito vai por `dataref`. Achados que afetam este SDD: correlação por `.data.x` com fato restrito; inbox inline; `read: envelope/raw` devolve o `dataref`.
- **Sandbox** ("Plano: Sandbox — validação da Fase 3", S.8–S.10): três papéis (Representante de Negócio, Representante Técnico, Técnico); revisão de decisão incerta; aprovação de documento com nota e **reprovação parcial** de itens de um lote (SDDs); prazos com lembrete e escalonamento; resposta de papel errado não destrava; DLQ com decisão do Técnico (reenviar com nota, aceitar, cancelar).

### 1.3 Conclusão
O motor já tem quase tudo: `emit` com `subject` e extensões, `listen` com correlação por envelope, filtro `with`, timeout com timer longo, `try/catch`. Faltam: um jeito de **voltar ao ramo da decisão**, o **registro de correção**, a **auditoria** das respostas ignoradas e o **contrato** dos eventos de revisão. Nenhuma mudança grande no `listen`.

## 2. Problema e objetivo
Fechar o laço humano: pedir uma revisão (decisão incerta ou aprovação de documento) a um papel, esperar a resposta com prazo, lembrete e escalonamento, seguir pelo caminho que o humano escolheu e transformar cada correção em dado de avaliação. Sem conteúdo em evento, log, span ou inbox; sem identidade de pessoa no Stint.

## 3. Requisitos
1. **RF1, forma na DSL** (8a): um passo de revisão, extensão do Stint validada pelo `STRICT`, para os dois usos: revisão de decisão e aprovação de documento.
2. **RF2, contrato de eventos:** `io.stintflow.review.requested.v1`, `io.stintflow.review.reminder.v1`, `io.stintflow.review.completed.v1`, com só ids, nomes declarados no YAML e ponteiros.
3. **RF3, retomada no ramo** (8b): o valor revisado volta ao roteamento da decisão; o registro original fica intacto e a correção é registro próprio.
4. **RF4, correlação e papel** (8c): por id de revisão em `subject`, sem `.data`; o papel é filtro; resposta de outro papel, de `source` não confiável, fora do contrato ou atrasada não retoma, e fica registrada.
5. **RF5, prazo:** lembrete antes do prazo; no prazo, escalonar para outro papel, aplicar um valor padrão ou falhar com `timeout` tratável.
6. **RF6, o que o revisor vê:** só ponteiro para o material redigido e o nível; nada inline no inbox.
7. **RF7, registro de correções:** por `WorkflowRef`, com retenção; exportação JSONL respeitando o nível.
8. **RF8, canal mínimo:** contrato documentado e um canal de exemplo HTTP no exemplo de IA. Sem UI.

## 4. Especificação

### 4.1 Forma na DSL (RF1): ver 8a
Recomendação: **(B) açúcar compilado**, em duas entradas que compartilham a mesma expansão.

**Revisão de decisão**, como bloco no `onUncertain` do `call: decision` (o `onUncertain` com nome de tarefa continua valendo):
```yaml
- meetingType:
    call: decision
    with:
      task: decide-meeting-type
      kind: choice
      input: ${ { text: .redactedText } }
      options:
        - business-design:   { then: draftDesign }
        - tech-refinement:   { then: refine }
        - out-of-scope:      { then: end }
    onUncertain:
      review:                               # Stint extension
        role: business-rep                  # the role that may answer (required)
        material: ${ .redactedRef }         # a pointer (URI) to the redacted material (required)
        deadline: { hours: 24 }             # required
        remind: { hours: 20 }               # optional, before the deadline
        escalate: { role: technical-rep, after: { hours: 24 } }   # optional
        onTimeout: { value: out-of-scope }  # or: fail (default) — a 'timeout' error a catch can handle
```
O humano escolhe uma das opções; o fluxo segue pelo `then` dela, como se a decisão tivesse saído com aquele valor (4.3).

**Aprovação de documento**, como tarefa:
```yaml
- approveSdds:
    call: review                            # Stint extension
    with:
      kind: approval                        # approval | choice
      role: technical-rep
      material: ${ .batchRef }
      items: ${ [ .sdds[].id ] }            # optional: ids reviewed one by one (partial rejection)
      deadline: { hours: 48 }
      remind: { hours: 40 }
      escalate: { role: technician, after: { hours: 24 } }
      onTimeout: fail
    onReject: reviseSdds                    # Stint extension: where any rejection goes
    then: publishBatch                      # where an approval goes
```
- `kind: choice` em `call: review` leva `options` (como na decisão) e roteia pelo `then` de cada uma: serve à decisão do Técnico na DLQ do S.10 (reenviar, aceitar, cancelar).
- **Saída** da tarefa (o que `output.as`/`export.as` veem): `{ verdict, value, rejectedItems, items, noteRef, role, reviewer, reviewedAt, reviewId }`. `rejectedItems` é a lista de ids reprovados; `noteRef` e cada `items[].noteRef` são ponteiros (4.6).
- **Chaves aceitas no `STRICT`:** na tarefa, `COMMON_TASK_KEYS` + `call`, `with`, `onReject`; em `with`, `kind`, `role`, `material`, `items`, `options`, `deadline`, `remind`, `escalate`, `onTimeout`; em `escalate`, `role` e `after`; em `onTimeout`, `value` ou o texto `fail`. Qualquer outra chave falha a carga com o caminho. `onReject` fora de `call: review kind: approval` falha. `review` dentro de `onUncertain` aceita as mesmas chaves de `with`, menos `kind`, `items` e `options` (vêm da decisão).
- **Validação na carga:** `remind < deadline`; prazos dentro do `maxDelay` do timer; papéis são nomes (`[a-z0-9-]+`); `onTimeout.value` é uma opção declarada; todo `then`/`onReject` resolve no mesmo fluxo.
- **Só no fluxo**, como o `call: redact`: não como corpo de `try`. Para tratar o `timeout` do `onTimeout: fail`, envolve-se a tarefa seguinte, ou usa-se `onTimeout: { value: ... }`.

**Expansão** (irmãos no mesmo `do`, nomes `<tarefa>/review/...`, todos DSL 1.0 com as extensões do Stint):
1. `emit` do `requested` (4.2) para o papel 1;
2. `try { listen }` com `timeout = remind` (se houver), `catch timeout` → `emit reminder` → `try { listen }` com o restante do prazo;
3. no vencimento: com `escalate`, `emit requested` para o papel 2 e `try { listen }` com `escalate.after`; sem `escalate` ou no fim dele, `onTimeout` (`set` do valor padrão, ou o `timeout` sem `catch`, que propaga);
4. `switch <tarefa>/review/route`: por `value` (escolha) ou `verdict` (aprovação), com os `then` declarados.

Cada fase do `listen` usa um nome de correlação próprio (`review-1`, `review-2`, `review-3`), para que as chaves de espera difiram e a troca de fase não apague e recrie a mesma chave na mesma transação do DynamoDB. O mesmo evento casa qualquer fase (mesmo `subject`), e só a fase ativa tem espera.

### 4.2 Contrato dos eventos (RF2)
| Tipo | Quem publica | `subject` | Extensões | `data` (só ids, nomes e ponteiros) |
|---|---|---|---|---|
| `io.stintflow.review.requested.v1` | o engine (`emit` gerado) | `reviewId` | `stintrole`, `stintsensitivity`, linhagem (2.5) | `{ reviewId, kind, role, options:[{name, description}], items:[ids], materialRef, deadline, escalatedFrom?, definition, pointer }` |
| `io.stintflow.review.reminder.v1` | o engine | `reviewId` | `stintrole`, linhagem | `{ reviewId, role, deadline }` |
| `io.stintflow.review.completed.v1` | o canal | `reviewId` | `stintrole` (papel de quem respondeu) | `{ verdict?, value?, items?:[{id, verdict, noteRef?}], noteRef?, reviewer }` |

- `io.stintflow.review.` entra nos prefixos reservados: um `emit` do autor com esse tipo falha a carga. O `completed` vem de fora, pelo canal de domínio, como qualquer evento que um `listen` espera.
- **Sem texto livre:** a nota do revisor vai por ponteiro (`noteRef`), guardado pelo canal sob a política do nível. Uma resposta com campo de texto fora do contrato (`note`, ou qualquer chave desconhecida) não retoma e é registrada (4.4).
- `reviewer` é um **id opaco** dado pelo canal (o canal pseudonimiza). O Stint nunca recebe nome ou e-mail: um `reviewer` com `@` ou espaço é recusado como fora do contrato.
- **Exceção ao `dataref` do 3a.5:** os eventos de revisão são montados pelo engine só com nomes declarados no YAML, ids e ponteiros. Por isso vão inline mesmo de instância restrita. `materialRef` precisa avaliar para um texto com esquema de URI (`s3://`, `file:`, `https://`…); qualquer outra coisa falha o passo com `configuration` (500), sem emitir.

### 4.3 Retomada no ramo escolhido (RF3): ver 8b
- O `switch <tarefa>/review/route` gerado para a revisão de decisão reusa os casos de opção do `<tarefa>/route` (mesmos `then`). O valor que o fluxo usa dali em diante é o **valor humano**.
- O resultado que o `output.as`/`export.as` do autor vê depois da revisão tem **a forma do resultado da decisão** (`value`, `confidence`, `uncertain`, `provenance`) com `value` humano, `uncertain: false`, `confidence: null` e `reviewed: { role, reviewer, reviewId, reviewedAt }`. O autor escreve um único `output.as`.
- **O registro de decisão original não muda**: `decisions["/do/i/meetingType"]` continua com valor, confiança e procedência do adapter.
- **A correção é registro próprio**, em `decisions["/do/i/meetingType/review"]`: `{ reviewId, originalValue, value, role, reviewer, requestedAt, reviewedAt, escalated, late:false }`, gravado na mesma `save` que aplica a resposta; e uma entrada no registro de correções (4.7).
- Aprovação de documento: o mesmo registro, com `verdict`, `rejectedItems` e `noteRef` no lugar de `value`.

### 4.4 Correlação, papel e confiança (RF4): ver 8c
- **Correlação por `subject`:** `correlate.review-k.from: '${ .subject }'`, `expect: '${ $review.id }'`. Funciona com fato restrito (nada em `.data`), fechando o achado do 3a.5 para este caso. O achado geral (correlação por `.data` de fato restrito) segue aberto.
- **`reviewId`:** `<instanceId>:<ponteiro>:<n>`, com `n` = quantas revisões daquele ponteiro a instância já pediu (como o `count` da decisão, 3a.1 5.4). Um `goTo` que volta à mesma revisão gera id novo, e uma resposta atrasada da anterior não casa. O engine expõe o id às expressões geradas como `$review.id` (detalhe de implementação, sem efeito fora delas).
- **Papel:** `with: { stintrole: <papel da fase> }` no filtro gerado. Uma resposta de outro papel casa a chave e falha o `with`: hoje é ignorada sem registro (1.1). **Mudança mínima no `listen`:** o `ListenNode` ganha um campo opcional `review` (o que a expansão sabe: papel por fase, opções, itens, ponteiro da decisão). Quando ele existe, o engine **registra** cada evento ignorado (auditoria `review`, outcome `wrong-role`, `untrusted-source`, `out-of-contract` ou `late`) e **valida** a resposta antes de consumir: `value` entre as opções, `verdict` conhecido, `items` iguais aos pedidos. Inválida, não consome e a instância segue esperando. Aditivo; o `listen` sem `review` não muda.
- **Confiança no `source`:** autenticação é do canal; o Stint confia no `source`. Regra: a política da definição declara os canais, `x-stint-policy.review.sources: [https://portal.sandbox.example]` (ou o engine, `WorkflowEngine.reviewSources(...)`, para todas). O filtro gerado só aceita esses `source`. Sem nenhum declarado, a carga do `call: review` falha (falha fechada). `source` desconhecido: não retoma, auditoria `untrusted-source`, WARN com ids.
- **Responsável pela resposta errada:** o canal deve recusar na origem. O Stint é a segunda barreira e o registro.

### 4.5 Prazo, lembrete e escalonamento (RF5)
- Prazos pelos timers do `listen`: curtos pelo SQS, longos pelo EventBridge Scheduler (2.4), sem mudança.
- `remind`: o `listen` da fase 1 vence em `remind`; o `catch` gerado emite o `reminder` e espera o restante (`deadline − remind`).
- No `deadline`: `escalate` → novo `requested` para o papel 2 (`escalatedFrom` = papel 1) e espera `escalate.after`; depois, `onTimeout`.
- `onTimeout: { value }`: segue como se o papel tivesse respondido esse valor, com `reviewer: null` e `defaulted: true` no registro; **não** entra no conjunto de avaliação (4.7).
- `onTimeout: fail` (padrão): erro `timeout` (408) no ponteiro da tarefa, como o do `listen` hoje.
- **Resposta atrasada** (papel 1 depois do escalonamento): casa a chave, falha o `with` do papel 2, auditoria `late`, não retoma.
- **Resposta duplicada:** a primeira consome; uma redelivery do mesmo evento é descartada (`alreadyConsumed`); outra resposta depois da retomada não encontra espera (vai ao inbox até a janela e expira, nunca aplicada).
- **Instância encerrada:** idem, nunca aplicada. Fica no DEBUG; sem auditoria, porque o engine não sabe a quem ela pertence.

### 4.6 O que o revisor vê (RF6)
- O pedido leva `materialRef` e o nível (`stintsensitivity`). O canal lê o material sob a política do nível (3a.5). O Stint não verifica que o material é a versão redigida: o autor aponta para ela (o `export.as` do `call: redact` é o lugar natural).
- Nada de conteúdo no evento, no log (ids, papel, `reviewId`, outcome) ou no span (ids de 2.5).
- **Inbox:** as respostas não têm texto livre (nota por ponteiro), e uma resposta com conteúdo é fora do contrato. Assim nenhuma resposta, restrita ou não, deixa conteúdo inline no inbox. Os pedidos nunca vão ao inbox (são publicados pelo engine, não esperados). Fecha o achado do 3a.5 para este caso.

### 4.7 Registro de correções e conjunto de avaliação (RF7)
- Porta nova no SPI, `CorrectionLog`: `append(Correction)`, `of(WorkflowRef)`; adapters `InMemoryCorrectionLog` e `DynamoDbCorrectionLog` (tabela `stint-corrections`, partição `definition` canônica, ordenação `instante#sequência`, `expiresAt` com a retenção da classe `corrections` da política, padrão **400 dias**, como a auditoria).
- `Correction`: `definition`, `instanceId`, `pointer`, `reviewId`, `kind`, `sensitivity`, `materialRef` (ponteiro, nunca inline), `decision` (`value`, `confidence`, `uncertain`, `provenance` do registro original; nulo em aprovação de documento), `human` (`value` ou `verdict`, `rejectedItems`, `noteRef`), `role`, `reviewer`, `requestedAt`, `reviewedAt`, `escalated`.
- Respostas por `onTimeout.value` não entram: não são correção humana.
- **Exportação JSONL:** `CorrectionExport.write(log, ref, maxLevel, Writer)`, uma linha por correção, só as de nível ≤ `maxLevel` (padrão `internal`); `materialRef` e `noteRef` como ponteiros. Ferramenta de linha de comando no módulo do exemplo.
- **Ferramenta de calibração offline: fora do escopo (recomendo).** O temperature scaling do 3a.2b age sobre a distribuição (`softmax(log p / T)`), e o registro guarda só a confiança **já calibrada** da opção escolhida, sem a distribuição bruta. Ajustar T com isso seria aproximação, e o CA6 mostrou que o problema é de modelo, não só de escala. Proposta: um SDD próprio, que antes acrescente a confiança bruta (ou a distribuição) ao registro de decisão. A exportação deste SDD já leva `adapter`, `confidence` e o acerto, o suficiente para medir a calibração (ECE) por adapter no sandbox.

### 4.8 Canal mínimo (RF8)
- O Stint entrega o contrato (4.2) no README e um canal de exemplo no `stint-example-ai-worker`: um endpoint HTTP com o `HttpServer` do JDK (sem extensão nova do Quarkus):
	- `GET /reviews` lista os pedidos abertos (ids, papel, opções, `materialRef`);
	- `POST /reviews/{reviewId}` com `stintrole` e `reviewer` no cabeçalho e `{ value | verdict, items, noteRef }` no corpo publica o `completed` com o `source` configurado.
- Sem autenticação no exemplo, documentado: quem confia é o canal real (portal do S.5).
- Sem UI.

### 4.9 Auditoria
- Kind novo `review` no `AuditLog` (3a.5): `requested`, `reminded`, `escalated`, `answered`, `defaulted`, `timed-out`, e os ignorados (`wrong-role`, `untrusted-source`, `out-of-contract`, `late`). Ids, papel e outcome; nunca valores de dado.

| Aderência à DSL 1.0 | Total | Extensão do Stint, como `call: decision`; o expandido é DSL 1.0 + `call: remote` | `run` é DSL 1.0, mas o subconjunto não existe |

- **Recomendação: (B).** É o mesmo caminho do `call: decision` e do `call: redact`, e é o único em que o engine sabe que um `listen` é uma revisão — condição para validar a resposta, registrar ignorados e gravar a correção. (A) fica documentado como o "expandido" que o autor pode ler. (C) seria outro SDD.

### 8b. Retomada no ramo escolhido (**decidido: proposta**, aprovado em 13/10/2026)
- **Proposta (4.3):** o `switch` gerado reusa os casos da decisão; o resultado da revisão tem a forma do resultado da decisão, com `value` humano e `reviewed`; registro original intacto; correção em `decisions[<ponteiro>/review]` e no `CorrectionLog`.
- **Alternativa:** reescrever `decisions[<ponteiro>]` com o valor humano e guardar o original dentro dele. Mais simples de ler, mas contraria "não apague nem reescreva o registro original". Não proponho.
- **Alternativa 2:** o resultado da revisão com forma própria (`{ human: … }`), e o autor escreve dois `output.as`. Mais explícito, mais propenso a erro. Não proponho.

### 8c. Correlação e papéis (**decidido: proposta**, aprovado em 13/10/2026)
- Correlação por **`subject` = `reviewId`** (sem `.data`, funciona com fato restrito). Alternativa: extensão `stintreviewid`. O `subject` é atributo padrão do CloudEvents, feito para isso ("the subject of the event in the context of the event producer"); prefiro.
- Papel por **`with: { stintrole }`**, que o `listen` já tem; a única mudança no `listen` é o campo opcional `review` para **registrar** os ignorados e **validar** a resposta antes de consumir. Não é mudança grande: o `listen` sem `review` não muda.
- `source` confiável **declarado na política** (`x-stint-policy.review.sources`) ou no engine; sem declaração, `call: review` não carrega. Desconhecido: ignorado e auditado.
- **Alternativa mínima:** checagem pós-retomada que volta a esperar. Descarto: retomar e voltar a esperar gera duas `save`s, um caminho de "desfazer" no interpretador e uma janela em que a instância está fora da espera. O `with` já faz isso antes de consumir.

### 8d. Prazo e lembrete
- Lembrete e escalonamento por fases de `listen` com nomes de correlação distintos (4.1), sem segundo timer no `listen`. Alternativa: um timer de lembrete dentro do `listen` (mudança no engine). Não proponho.

### 8e. Registro de correções
- Porta própria (`CorrectionLog`) em vez de reusar o `AuditLog`: a auditoria é por instância e só ids; a correção é por definição, leva valores declarados (opções) e ponteiros, e é exportada. Retenção 400 dias pela classe `corrections`.
- Calibração offline fora do escopo (4.7).

### 8f. Tamanho
- O SDD é maior que o 3a.1. Opção de dividir em **3a.4a** (forma, eventos, correlação, papéis, prazos, retomada) e **3a.4b** (registro de correções, exportação, canal). Recomendo **não dividir**: o CA3 depende das duas metades, e o sandbox precisa das duas para o S.8.

### 9.3 Desvios e decisões da implementação (para sua revisão)
- **Id da revisão sem expressão:** a spec previa `$review.id` nas expressões geradas. Fiz mais simples: o engine dá o id ao pedido (no `commit`, a partir do registro em `decisions`) e os `listen` de revisão correlacionam por esse id, sem avaliar `expect`. Mesmo efeito, sem variável nova no jq.
- **Papel checado pelo engine antes do `with`:** o filtro gerado tem `with: { stintrole }`, como na spec, mas o engine checa papel, `source` e contrato antes, para poder auditar o motivo. Sem isso, o `with` descartaria em silêncio.
- **`source` só pela política:** `x-stint-policy.review.sources`. A opção "ou no engine" (`reviewSources(...)`) ficou de fora; sem `sources`, a revisão não carrega.
- **`onTimeout: fail`** falha a instância com `timeout`: como o passo de revisão só existe no fluxo (não num `try`), não há `catch` para ele. Quem quer seguir em frente usa `onTimeout: { value }`.
- **Padrão por prazo** (`onTimeout.value`) não tem auditoria `defaulted` própria: é um `set` gerado. O resultado leva `defaulted: true`, e não há correção.
- **`material` no `onUncertain.review`** é avaliado sobre o resultado da decisão, com `$context` disponível: o autor escreve `${ $context.redactedRef }`.
- **Booleanos:** a revisão de uma decisão `boolean` usa as opções `true`/`false`; o `switch` compara `(.value | tostring)`.

### 9.4 Achados (fora do escopo, não feitos)
- **Resposta adiantada de outro papel:** cada fase correlaciona sob um nome próprio, e um evento é tentado em todas as chaves. Uma resposta do papel 2 durante a fase 1 é recusada (`wrong-role`), mas fica no inbox sob a chave da fase 3, sem conteúdo, até a janela. Se o escalonamento acontecer dentro dela, essa resposta é aceita. Vale um SDD curto se o sandbox quiser proibir.
- **Resposta para instância encerrada** fica no inbox (sem conteúdo) até a janela, nunca é aplicada e não é auditada: o engine não sabe a quem pertence.
- Os achados gerais do 3a.5 seguem abertos fora do caso de revisão: correlação de `listen` por `.data` de fato restrito; `read: envelope`/`raw` com `dataref`.
- **Calibração offline** (4.7): fora do escopo, como aprovado.
