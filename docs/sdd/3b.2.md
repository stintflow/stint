### 1.2 Achados que mudam o desenho
1. **O pseudônimo do 3a.5 não serve a um grafo.** Ele muda por instância (de propósito) e tem só **24 bits** (`PERSON_3f9a2c`): colide por acaso em milhares de pessoas. Um nó `Person` precisa de id estável entre reuniões e com colisão desprezível. Isso exige um modo novo de pseudônimo, por escopo (decisão 8d).
2. **O apagamento por pessoa só é possível com id estável por escopo.** O pedido de apagamento chega com identidade (e-mail, nome); o serviço de apagamento recalcula o HMAC e acha o nó. Com pseudônimo por instância não há como achar a pessoa sem varrer tudo.
3. **A resolução precisa ler a base.** A porta do 3b.1 não tinha consulta de entidade por nome; foi acrescentada (`entities`).
4. **Duplicata é do 3b.6, mas o critério nasce aqui.** Se a extração e o 3b.6 usarem regras diferentes, o que uma marca como candidato o outro não enxerga. Um único critério, versionado, no `stint-knowledge`.

## 2. Problema e objetivo
Transformar a transcrição **já redigida** de uma reunião em entidades e relações de um esquema versionado, sem inventar tipos, sem criar nó duplicado quando o termo já existe e sem pôr dado pessoal no grafo, a um custo de tokens limitado. A saída é um `KnowledgeBatch` do 3b.1, pronto para o passo de escrita.

## 3. Requisitos
**Funcionais**
1. **RF1, esquema versionado** por definição, com os 7 tipos de nó e as 6 relações (4.1).
2. **RF2, versão no log:** `schemaVersion` entra no lote e, daí, em toda entrada do log do 3b.1 (4.2).
3. **RF3, extração** com saída estruturada validada contra o esquema; fora do esquema é `validation` 400 (4.3).
4. **RF4, glossário** no prompt e **resolução** para ids existentes antes de criar nó (4.4).
5. **RF5, critério de duplicata candidata** único e versionado, compartilhado com o 3b.6 (4.5).
6. **RF6, pessoa** só como pseudônimo, com mapa conforme a política, alinhado ao apagamento do 3b.5 (4.6).
7. **RF7, custo:** limite de tokens e estratégia de glossário relevante (4.7).
8. **RF8, avaliação:** conjunto sintético em inglês para resolução de entidades (4.8).

**Não funcionais**
- **RNF1:** `stint-knowledge` continua sem IA, sem nuvem e sem `stint-core`. LangChain4j só em `io.stintflow.worker.langchain4j` (regra existente). Nada do lado do engine depende do esquema.
- **RNF2:** sem mudança no wire nem no SPI. Mudança aditiva no `stint-dsl` só se 8a escolher a declaração na definição.
- **RNF3:** dados sempre sintéticos, com varredor de `SYNTH-PII-*` na saída da extração e no grafo.
- **RNF4:** testes de CI sem modelo (resolução, validação, glossário). O teste com modelo é execução manual.

## 4. Especificação

### 4.1 Esquema versionado (item a)
**Arquivo de esquema** (YAML ou JSON, imutável por versão), no `stint-knowledge`, pacote `io.stintflow.knowledge.schema`:
```yaml
schema: meetings          # id
version: 1.0.0            # semver
language: en
nodes:
  Meeting:       { key: meetingId,  defaultSensitivity: internal,
                   properties: { meetingId: {type: string, required: true}, heldOn: {type: date}, title: {type: string, sensitive: true} } }
  Person:        { key: pseudonym,  defaultSensitivity: confidential,
                   properties: { pseudonym: {type: string, required: true, pattern: 'PERSON_[0-9a-f]{32}'} } }
  Decision:      { key: key,        defaultSensitivity: internal,
                   properties: { key: {type: string, required: true}, summary: {type: string, required: true, sensitive: true}, status: {type: enum, values: [proposed, accepted, rejected]} } }
  Requirement:   { key: key,        defaultSensitivity: internal,
                   properties: { key: {type: string, required: true}, summary: {type: string, required: true, sensitive: true} } }
  System:        { key: name,       defaultSensitivity: internal,  glossary: true,
                   properties: { name: {type: string, required: true} } }
  Term:          { key: name,       defaultSensitivity: internal,  glossary: true,
                   properties: { name: {type: string, required: true}, definition: {type: string} } }
  ExternalReference: { key: url,    defaultSensitivity: internal,
                   properties: { url: {type: string, required: true}, kind: {type: enum, values: [ticket, document, repository, other]} } }
relations:
  participated: { from: [Person],                       to: [Meeting] }
  decided:      { from: [Meeting],                      to: [Decision] }
  supersedes:   { from: [Decision, Requirement],        to: [Decision, Requirement], sameType: true }
  affects:      { from: [Decision, Requirement],        to: [System, Requirement] }
  mentions:     { from: [Meeting, Decision, Requirement], to: [Term, System, ExternalReference] }
  motivated-by: { from: [Decision],                     to: [Requirement, ExternalReference] }
```
- **Regras:** tipo ou relação que o esquema não lista não existe; propriedade que o esquema não lista é recusada; relação só entre os tipos permitidos (`sameType` exige o mesmo tipo nas duas pontas).
- **`defaultSensitivity` e `sensitive`:** o nível de um item é `max(defaultSensitivity do tipo, nível da instância no momento da escrita)`. Propriedade `sensitive: true` (texto livre) vai para o blob quando o item é restrito (E1 do 3b.1). `Person` nunca tem propriedade com nome (4.6).
- **Chave natural (`key`)** de cada tipo: o campo que, normalizado, entra no id determinístico do 3b.1 (`EntityIds.of(type, chave)`).
- **Como a definição declara (decisão 8a):**
  ```yaml
  document:
    metadata:
      x-stint-knowledge:        # Stint extension, like x-stint-policy
        base: product-meetings  # optional; default: namespace + name (3b.1, 4.3)
        schema: meetings@1      # id@major; the worker resolves the latest 1.x it knows
        glossary: product-glossary@1
  ```
  - O `STRICT` do `stint-dsl` valida só a **forma** (chaves conhecidas, `id@major`). O `stint-dsl` não pode depender do `stint-knowledge`, então a resolução do esquema é do worker, por um `SchemaRegistry` configurado nele.
  - **Alternativa:** só no worker, por propriedade (`stint.knowledge.schema=meetings@1`), sem tocar o DSL. Recomendo a declaração na definição: a versão do esquema acompanha a versão da definição, e o log registra as duas.
- **Evolução:**
  - minor (`1.1`): só acrescenta tipo, relação ou propriedade **opcional**; dado escrito em 1.0 continua válido;
  - major (`2.0`): remove ou renomeia; exige migração (fora de escopo, 3b.6);
  - `(id, versão)` é imutável: o registro guarda o hash do conteúdo e recusa outra definição com a mesma versão.

### 4.2 A versão do esquema no log de mudanças
- O lote carrega `schemaVersion = "<id>@<semver completo>"` (por exemplo `meetings@1.0.0`), e o 3b.1 copia o valor para cada `ChangeEntry` (3b.1, 4.5). Lote sem a versão é inválido.
- Lote cujo esquema tem `id` diferente do da base é recusado; `major` diferente do já presente na base é recusado até a migração.
- A proveniência da **extração** (modelo, versão do prompt, versão do glossário) não vai para o log do grafo: vai para a `AuditLog` (`ai-call`, `detail`), sem texto, e o lote guarda a `definition` completa em `Source`.

### 4.3 Worker de extração (item b)
`KnowledgeExtractionWorker`, em `stint-worker-langchain4j` (pacote principal; é onde LangChain4j é permitido), com `LlmDecisionAdapter` como molde:
- **Entrada** (rota `extract-knowledge`): `passages` (texto **redigido**, `ordinal`, `language`), `documentId`, `meeting` (`meetingId`, `heldOn`), `schema` (id@versão). O worker recusa entrada cujo nível seja `restricted` com provedor remoto (`SensitivityPolicy`, sem mudança).
- **Divisão em trechos:** `PassageSplitter` determinístico (por turno de fala, teto de caracteres), no `stint-knowledge`, para os ids de trecho do 3b.1 serem estáveis entre execuções.
- **Saída estruturada:** o `JsonSchema` do provedor é **gerado** do esquema (`SchemaJson.of(schema)`), e a resposta é `ExtractionResult { entities[{ref, type, mention, properties, passages[]}], relations[{type, from, to}] }`, onde `ref` é um rótulo local da resposta e `passages` são ordinais.
- **Validação (`SchemaValidator`, no `stint-knowledge`, puro):** tipo e relação conhecidos, pontas do tipo certo, propriedade conhecida, obrigatória, do tipo e do formato (enum, `pattern`), `ref` único e resolvido, ordinal existente, limites de tamanho. As violações citam **campo e regra, nunca valor**, como o `OutputValidator`.
- **Fora do esquema:** a tarefa falha com `ErrorInfo` `validation` (400), `instance` = ponteiro da tarefa, `detail` com as violações. **Sem aceitação parcial e sem reparo automático** (padrão `repairAttempts = 0`; o fluxo trata com `catch` e, se quiser, revisão humana). O motivo: um lote parcial grava um grafo que ninguém revisou.
- **Saída da tarefa:** um `KnowledgeBatch` do 3b.1 (ids determinísticos, ligações trecho↔entidade, `schemaVersion`, `Source`), não um texto. O passo de **escrita** no store é do 3b.3.

### 4.4 Glossário, resolução e ids existentes (item c)
- **Glossário** (`Glossary`): lista versionada de `{ id, type, canonicalName, aliases[≤8], definition (≤ 80 caracteres) }`, em inglês, por tipo de nó com `glossary: true` (`System`, `Term`). Fonte: arquivo da definição ou entidades já na base (`entities(...)`).
- **No prompt:** só o subconjunto relevante (4.7), em linhas compactas `id | nome | aliases`, com a instrução: "se a menção for um destes termos, use o `id`; só crie um tipo novo se nenhum servir".
- **Resolução, em ordem, antes de criar qualquer nó** (`EntityResolver`, determinístico, sem IA, no `stint-knowledge`):
  1. `id` do glossário citado pelo modelo, **conferido** (existe e é do tipo certo; senão, ignorado);
  2. nome normalizado igual ao nome canônico ou a um alias do glossário;
  3. mesma chave natural normalizada de uma entidade já na base (`entities(...)`, respeitando o teto de sensibilidade);
  4. senão, **nó novo**, com id `EntityIds.of(type, chave)`. Quando houver candidata (4.5), a extração **não funde**: cria o nó e devolve o par em `duplicateCandidates`.
- **Nunca funde por semelhança.** Funde só quando 1, 2 ou 3 casam exatamente (normalizado). Fundir errado destrói conhecimento e é pior do que duplicar.
- O resultado carrega, por entidade, `resolution: glossary | alias | existing | new`, para métricas.

### 4.5 Critério de duplicata candidata, compartilhado com o 3b.6
`DuplicateCriterion` (`stint-knowledge`, versionado: `duplicate-criterion/1`), função pura `(Entity a, Entity b) → Optional<Candidate(score, reasons)>`:
- só entre o **mesmo tipo**;
- candidata se: (i) alguma chave ou alias normalizado de `a` é igual a algum de `b`, **ou** (ii) a semelhança do nome normalizado ≥ **0,85** (Jaro-Winkler sobre os tokens ordenados) **ou** (iii) mesmo `url` (para `ExternalReference`);
- **nunca** para `Person` (pessoa não é candidata por semelhança de pseudônimo);
- o limiar e a versão ficam no código do critério e na saída (`criterionVersion`); mudar o limiar muda a versão.
- O 3b.2 só **marca** (`duplicateCandidates` na saída). Guardar, revisar e fundir é do 3b.6, que chama a mesma função.

### 4.6 Pessoa como dado pessoal (item d)
- **O esquema não tem nome.** `Person` tem uma propriedade só, `pseudonym`. Qualquer outra propriedade, ou um `pseudonym` fora do formato, é violação de esquema. Isso falha fechada quando o modelo recebeu um nome sem redação.
- A extração **nunca escreve nome** no grafo, nem em trecho: o texto de entrada já passou por `call: redact`. O varredor de `SYNTH-PII-*` roda sobre a saída (CA).
- **Id de pessoa (decisão 8d):** o pseudônimo do 3a.5 não serve (achado 1). Proposta:
  - **P2 (recomendada):** novo modo opt-in no redator, `Pseudonyms.scoped(secret)`: `PERSON_<32 hex>` = HMAC-SHA-256(segredo do escopo, `escopo`, `tipo`, valor normalizado), **128 bits**, **sem `instanceId`**. O mesmo nome dá o mesmo id em todas as reuniões da base, e só nelas. Ligado por `x-stint-policy.pseudonyms: { stable: scope }`, desligado por padrão. É uma correlação **deliberada** e fica na auditoria da política.
  - **P1:** manter só o pseudônimo por instância: cada reunião tem as suas pessoas e `participated` não liga reuniões. Não correlaciona, mas o grafo perde o valor principal e o apagamento por pessoa deixa de ser possível.
  - **P3:** mapa reversível em cofre (`reversible(...)` do 3a.5). Permite mostrar o nome, mas põe um mapa de identidades de longa vida no sistema; só com política explícita.
- **Mapa e política (alinhado ao 3b.5):**
  - sem P3 **não existe mapa** identidade→pseudônimo: ele é recalculável por quem tem o segredo;
  - **apagamento por pessoa (3b.5):** o serviço recebe a identidade, calcula o id com o segredo, e chama `delete(ByPerson(id))` do 3b.1; apaga nó, arestas, ligações e (padrão) trechos ligados. Se existir cofre (P3), a entrada dele é apagada na mesma ação, e isso é registrado;
  - **rotação ou destruição do segredo** torna os pseudônimos irrecuperáveis (apaga a capacidade de achar a pessoa, não os nós já gravados): é um recurso de 3b.5, não uma forma de apagamento;
  - o segredo do escopo vive no cofre do worker, nunca no Stint nem no log.
- O nível padrão de `Person` é `confidential` (4.1), então o nó entra no índice só com teto ≥ `confidential`.

### 4.7 Custo de tokens com glossário grande (item f)
**Regra: nunca o glossário inteiro.** Por chamada, `GlossarySelector`:
1. **Lexical:** índice invertido de tokens de nome e alias; termos cujos tokens aparecem na janela de trechos (acerto exato primeiro);
2. **Semântico (opcional):** `entities(...)` / vetor sobre a janela, se houver embedder;
3. **Teto:** `maxGlossaryTerms = 40` e `maxGlossaryTokens = 1 500` (estimado em caracteres/4). Passou do teto: ordena por (acerto exato, pontuação, id) e corta; métrica `glossaryTruncated`, sem falhar.
4. Linha compacta: `id | nome | até 3 aliases` (definição só se couber, ≤ 80 caracteres).
5. Ordem estável (por id) para o prefixo do prompt ser reaproveitável pelo provedor (cache de prefixo, quando houver).

**Janela:** os trechos vão em janelas de até `maxWindowTokens = 3 000`; o glossário é escolhido **por janela**.

**Orçamento estimado por chamada** (a medir): instruções ≈ 600, esquema ≈ 400, glossário ≤ 1 500, janela ≤ 3 000, saída ≤ 1 500 → **≤ ≈ 7 000 tokens**. Uma reunião de 45 minutos (≈ 7 000 palavras, ≈ 10 000 tokens) dá ≈ 4 janelas, ≈ 28 000 tokens.
- `maxTokensPerDocument = 40 000` (padrão). Estourou: a tarefa para e falha com `configuration`/`validation`? **Proposta:** falha com `runtime` 500 e `detail` com contagens, sem gravar nada (nenhum lote parcial).
- Medição por `UsageSink` (3a.3) e `DecisionUsageSink`; o relatório do 3a.6 ganha tokens por janela e `glossaryTruncated`.

### 4.8 Conjunto de avaliação de resolução de entidades (item e)
**Base:** o corpus do 3a.6 (8 reuniões, inglês). Acréscimo **aditivo** ao formato (v1 → v1.1, chave opcional `kb:`):
```yaml
kb:
  entities:
    - { id: system:checkout-service, type: System, surface: ["checkout service", "Checkout", "the checkout svc"] }
    - { id: term:sla, type: Term, surface: ["SLA", "service level agreement"] }
  relations:
    - { type: affects, from: decision:d1, to: system:checkout-service }
  mustNotMerge: [ [system:payments-api, system:payments-ui] ]    # homônimos
```
- **Conteúdo:** os 8 roteiros existentes ganham `kb:` e entram **4 reuniões novas** (m-009 a m-012) desenhadas para a resolução. Cobrem:
  - alias e abreviação ("SLA" / "service level agreement");
  - maiúsculas, plural e pontuação;
  - erro de digitação simples;
  - **homônimos** que não devem fundir (dois sistemas de nome parecido);
  - termo já no glossário × termo novo;
  - decisão repetida entre reuniões (`supersedes`);
  - pessoa só por pseudônimo.
- Estimativa: ≈ 150 menções, ≈ 40 entidades. PII sempre `SYNTH-PII-*`. Entra no `manifest.json` com hash. Não altera o `expected` existente nem o `AiWorkerMainIT`.
- **Duas camadas:**
  - **Resolução (CI, sem modelo):** entrada = menções do gabarito; mede o `EntityResolver` e o `DuplicateCriterion`;
  - **Extração (manual, modelo local):** o worker sobre os roteiros; mede esquema e resolução de ponta a ponta.
- **Métricas:** precisão e revocação de resolução; **taxa de fusão errada** (`mustNotMerge`); revocação de candidatas; taxa de violação de esquema; tokens por janela.
- **Limiares de CI (resolução):** fusão errada **= 0**; revocação de alias e abreviação do glossário ≥ 0,95; revocação de candidatas ≥ 0,90. A extração não tem limiar: só relatório.

## 5. Critérios de aceite
- CA1 O esquema `meetings@1.0.0` carrega, e `(id, versão)` com conteúdo diferente é recusado.
- CA2 Tipo, propriedade ou relação fora do esquema, pontas erradas e `Person` com qualquer propriedade além de `pseudonym` falham na validação.
- CA3 Saída fora do esquema vira `validation` 400, com campos e regras e **sem valores**, e nada é gravado (sem lote parcial).
- CA4 O lote gerado leva `schemaVersion` e, escrito no store, toda entrada do log a carrega.
- CA5 A declaração `x-stint-knowledge` passa o `STRICT` (forma) e chave desconhecida falha com o caminho.
- CA6 A resolução funde só com casamento exato (glossário, alias, chave existente); semelhança nunca funde; `mustNotMerge` = 0 fusões.
- CA7 `DuplicateCriterion` é o mesmo código chamado pela extração e (testado por contrato) disponível ao 3b.6; mudar o limiar muda a versão.
- CA8 O glossário no prompt nunca passa de 40 termos nem de 1 500 tokens estimados, com um glossário de 5 000 termos; `glossaryTruncated` é contado.
- CA9 Estouro de `maxTokensPerDocument` falha sem gravar.
- CA10 O varredor de `SYNTH-PII-*` não acha marcador na saída da extração nem no grafo; `Person` só tem pseudônimo.
- CA11 (se 8d = P2) O mesmo valor dá o mesmo `PERSON_<32 hex>` em instâncias diferentes do mesmo escopo e outro em escopo diferente; o modo é desligado por padrão; nenhuma asserção do 3a.5 muda.
- CA12 Conjunto de avaliação: limiares de CI do 4.8 atendidos; manifesto com hash confere.
- CA13 ArchUnit: sem IA e sem nuvem em `stint-knowledge`; LangChain4j só no pacote principal do worker; `mvn verify` completo, sem mudar asserção existente.

### 9.4 Desvios e observações
- **Esquema em JSON, não em YAML**, e carregado de um recurso do módulo (`meetings-1.0.0.json`): o módulo não depende de biblioteca de YAML. A forma é a da spec.
- **O Notion e o rascunho do 3b.2/3b.6 não foram lidos** (conector fora do ar): a divisão `ExtractionPiecesTest`/worker/avaliação segue o texto da fila. Conferir 4.4 e 4.5 contra o 3b.6 quando o conector voltar.
- O corpus tem **121 menções**, não as cerca de 150 estimadas, e **as reuniões novas ficam sob `knowledge` no manifesto**, não sob `meetings`: assim o marco do 3a.6 (oito reuniões, áudio, métricas) não as executa e nenhuma asserção dele muda. Não há áudio para elas.
- Os casos do conjunto são fáceis por construção (aliases, caixa, erros de digitação, homônimos): 100 % é o piso esperado de um resolvedor determinístico, não uma medida da extração. A extração com um modelo é execução manual e não tem limiar; **não foi rodada** (nenhum modelo local foi usado nesta sessão).
- `ofType` do `EntityResolver.Existing` do worker devolve vazio: a porta da base não lista por tipo. As candidatas vêm do glossário e das buscas exatas.
- O custo de tokens usa caracteres/4 como estimativa, não o tokenizador do modelo: o teto por documento é uma garantia de ordem de grandeza, a medir na execução manual.
- A leitura de entidades existentes usa o teto de sensibilidade da própria instância. Um `Person` confidencial só é achado por uma instância ao menos confidencial.
- Não há ainda o passo que **escreve** o lote no store a partir da tarefa (3b.3): hoje o lote sai da tarefa como JSON (`KnowledgeBatchJson`) e a escrita é feita por quem chama.
